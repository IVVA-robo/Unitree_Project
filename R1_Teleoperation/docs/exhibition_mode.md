# Выставочный запуск без Codex

> Unitree Explore больше не нужен для выбора режима: read-only DDS capture
> подтвердил, что Lock и Run отправляют те же штатные `SetFsmId(4)` и
> `SetFsmId(811)`, которые уже использует официальный `LocoClient`. Перед
> выставочным запуском приложение на телефоне нужно полностью закрыть, чтобы
> освободить видеосессию и исключить второй виртуальный стик.

Выставочный manager объединяет проверки, Robot POV и уже проверенный live-путь
в шесть команд. Он работает локально, не требует интернета и пишет журналы в
`logs/exhibition/`. Manager сам не создаёт Unitree SDK-клиент, не публикует
команды роботу, не подделывает Deadman и не снимает KILL. Физический control
по-прежнему проходит через `teleop-live` и `robot-prepare`. Control-сеанс
запускается с явным `SAFETY_PROFILE=exhibition`: постоянный Deadman в нём не
нужен, но SDK/LowState/motor-health/limits и центральный KILL сохраняются.
Обычные кнопки LOCK и RUN запускаются одним нажатием без диалога с чекбоксами;
сеть, feedback, VR, writer и остальные машинно проверяемые условия по-прежнему
проверяются автоматически внутри запуска.

## Быстрый запуск

Открыть русскую панель:

```bash
cd /home/unitree/Unitree_Project/R1_Teleoperation
make exhibition-panel
```

Те же действия доступны из терминала:

```bash
make exhibition-static
make exhibition-control
make exhibition-full-live
make exhibition-reconnect
make exhibition-rearm
make exhibition-calibrate-arms
make exhibition-calibrate-head
make exhibition-stop
make exhibition-status
```

`exhibition-static` и `exhibition-control` — долгоживущие foreground-процессы.
Их не нужно запускать одновременно. Состояние и PID находятся в приватном
runtime-каталоге `$XDG_RUNTIME_DIR/r1-exhibition/`, но commissioning token и
другие значения окружения туда не записываются.

Перед созданием нового графа manager проверяет пользовательский
`r1-offline-session.service` и его точный `ExecStart`. Для **control/RUN**
совместимый video-only сервис по-прежнему останавливается только после
подтверждения, что это нужный unit; затем освобождаются UDP `9090/9091` и TCP
`8080`, а live-сеанс создаёт собственные VR bridge и POV. Исходное состояние
сервиса записывается в `exhibition-status`, и после STOP он восстанавливается.

Для **static/СТОЙКИ** здоровая служба и уже слушающий `:8080` Robot POV теперь
переиспользуются. Static writer запускается с `start_bridge=false`, поэтому не
занимает UDP `9090` и не создаёт второй видеосервер. Если unit несовместим,
его состояние нельзя проверить или POV отсутствует, быстрый путь не
принимается: manager использует прежний handoff/fallback. Robot POV настроен
на process-local respawn через 2 секунды, поэтому падение видеопроцесса не
перезапускает исправный VR bridge или всю offline-службу. Выборочный reconnect
ждёт это восстановление до 8 секунд и только затем использует restart unit как
fallback, оставляя static writer тёплым. Произвольные процессы по совпадению
имени manager не завершает.

На физическом R1 этот static reuse проверен 01.10.2026: существующие PID
offline-службы, POV и bridge не изменились, дубликатов не появилось, полный
manager start → стабильный FSM 4 занял `10,460 s`.

Принудительное завершение живого POV также проверено 01.10.2026. Новый POV
стал ready за `5,716 s`; PID offline-службы, родительского ROS launch, VR
bridge, static manager и writer не изменились, `NRestarts=0`. Healthy reconnect
после восстановления ничего не перезапустил.

## Статичный режим

Отдельная кнопка **СТОЙКА** всегда выбирает полный статический режим ниже,
в том числе при работающем VR: сначала подтверждённое завершение владельца
ArmSdk, затем новый static writer с StandUp/FSM 4 и без Start/FSM 811.
Кнопка не вызывает быстрый pause/rearm. Повторное нажатие при готовом static
сеансе ничего не перезапускает. Из стойки RUN выполняет полную подготовку.
Прежний LOCK и его быстрая пауза оставлены без изменения. Это штатная
моторная стойка; отключение внутренних контуров стабилизации не реализуется.

Если уже работает **Режим управления**, кнопка LOCK не останавливает DDS,
video, SDK reader или live writer. Панель вызывает `/vr/teleop/pause_session`:
ноги получают нулевую скорость, руки и голова переходят в hold, а подготовленный
control graph остаётся тёплым. Такой RUN → LOCK занимает только время одного
подтверждённого ROS service call. Полный статический запуск используется лишь
когда control graph ещё не запущен или восстанавливается после сбоя.

Manager выполняет read-only `robot-preflight`, переиспользует уже работающий
совместимый offline POV либо запускает собственный физический video-only
`pov-vr`. Затем запускается отдельный
`r1-live-session static`: bridge, HMD, руки, IK, стики и velocity pipeline в
нём отсутствуют, а `robot-prepare` вызывает только официальный high-level
`StandUp()` и подтверждает устойчивый FSM 4. FSM 811 и `SetVelocity` в этом
режиме недоступны. VR-шлем и контроллеры не нужны.

Статический writer сохраняет обязательные KILL, LowState, motor-health,
commissioning и SDK watchdog. После подтверждённого Stand он удерживает
cleanup debt: критическая ошибка, явный STOP, выход writer или завершение
manager вызывают проверенный `robot-stop` и официальный `StopMove`. Writer
самостоятельно не перезапускается. Признак
`ROBOT_CONFIRM_STATIC_PREPARE=1` manager передаёт только static writer и его
prepare; control-сеанс его не наследует.

`r1-exhibition-wait-ready` одним DDS participant проверяет все typed
services/topics, точные `transport=sdk`, `profile=slow-safe`, выключенные
head/arms/locomotion и token текущего writer. Для следующего процесса prepare
он создаёт одноразовую HMAC-аттестацию `0600` сроком 10 секунд, привязанную к
boot, UUID manager-сессии, ROS domain и commissioning token; сам token в файл
не записывается. После потребления prepare пропускает только повторные
discovery/parameter dump и общий VR/debug observer, который к featureless
static-графу неприменим. Финальный `2,25 s` ArmSdk idle/writer-count gate,
KILL release, writer prepare и стабильный FSM 4 остаются обязательными.
После traffic gate три service call и ожидание status выполняет один bounded
ROS participant (`r1-robot-prepare-client`), сохраняя прежний порядок и паузу
распространения KILL `0,3 s`. Это не объединяет safety gate с actuation и не
меняет аварийный supervisor/writer relock при ошибке.

## Режим управления

Control-stage запускает единый 13-суставный `ArmSdk` для головы, пояса и обеих
рук, а ноги — через официальный high-level `LocoClient`. Голова использует
отдельную HMD-neutral калибровку. Туловище для IK рук фиксируется в позе
калибровки: поворот HMD управляет головой робота и сам по себе не создаёт
команд рукам.

Manager выполняет следующую цепочку:

1. read-only `robot-preflight`;
2. Robot POV с безопасным автоматическим reconnect;
3. `teleop-live` (голова, руки и официальный high-level locomotion);
4. ожидание точных типов ROS-сервисов и feedback/command топиков;
5. автоматическая фиксация текущей позы HMD и каждого контроллера как
   независимой нулевой точки до включения управления; специальная T-поза не
   нужна (`R1_EXHIBITION_CALIBRATE_ON_START=0` отключает этот шаг);
6. явное включение выставочной session-arm защёлки;
7. `robot-prepare`, который проверяет SDK feedback, текущий FSM, VR,
   калибровку, KILL и commissioning acknowledgements;

Первый холодный robot-facing preflight на реальном R1 может занимать больше
минуты, поэтому manager даёт подготовке до 180 секунд. После того как этот
preflight выполнен и typed graph подтверждён, `robot-prepare` использует
связанный с commissioning token быстрый путь: один снимок параметров вместо
отдельного DDS-процесса на каждый параметр и двухсекундное финальное окно
ArmSdk traffic. Проверки свежего feedback, VR-команд, калибровки, KILL и
подтверждение официального prepare остаются обязательными.

В полном control-пути пассивный preflight дополнительно собирает одним DDS
participant те же данные, которые раньше читались шестью последовательными
`ros2 topic echo`: active/deadman, head status и trajectory, arm trajectory,
locomotion debug command и пять физических q/dq samples головы. Нестандартные
commissioning-конфигурации сохраняют старый fallback. После observer по-прежнему
обязательны отдельный `2,25 s` ArmSdk writer/traffic gate, KILL release/reset и
стабильное подтверждение FSM 4/811.

Кнопка **Найти и подключить** заранее запускает только read-only
`r1-sdk-warmup`. Он ждёт робота, выполняет полный SDK feedback preflight без
команд приводам и сохраняет приватную краткоживущую аттестацию. RUN принимает
её только на том же boot, интерфейсе, MAC/IP/ROS domain, при неизменившихся RX
error counters, наличии carrier/route/ping и отсутствии другого writer. При
любом несовпадении live launcher автоматически возвращается к полному
preflight. После запуска graph свежий LowState, motor health и отсутствие
ArmSdk traffic проверяются снова до снятия KILL.

Периодическое обновление запускается заранее, через 120 секунд, и сохраняет
последнюю исправную аттестацию до атомарной записи замены. Поэтому нажатие во
время здорового `REFRESHING` больше не попадает в пустое cache-window. При
потере carrier/ping, неуспешном preflight или новом владельце warmup кэш
инвалидируется как прежде; эта оптимизация не снимает KILL и не создаёт writer.

Переход panel-status `robot=OFFLINE → OK/READY` дополнительно заменяет
работающий warmup асинхронно: сначала подтверждённый выход старого владельца,
затем один новый read-only worker. Это устраняет зависимость кэша от процесса,
который пережил переподключение Ethernet. При первом `OK`, активном физическом
сеансе, Zero Torque, закрытии панели или ожидающей команде режима restart не
выполняется. Нажатие RUN/LOCK/СТОЙКИ отменяет фоновую очередь и получает
приоритет; автоматического движения после восстановления связи нет.

Обычный **LOCK → RUN** теперь вызывает `resume_ready`: один ROS-клиент
подтверждает свежий KILL=false, запрашивает возврат VR и проверяет свежие
active/session_armed/writer_armed. Повторная калибровка, StandUp/Start и
перезапуск SDK не выполняются. Панель распознаёт и сеанс, запущенный из
терминала. LOCK не сбрасывает post-prepare readiness через Deadman: в
выставочном режиме разрешение даёт session_armed; её снятие и B по-прежнему
останавливают writer. Это пауза нашего управления с hold/zero, а не обещание
одинакового внутреннего FSM со штатным Lock приложения.
IK также сохраняет уже проверенную нейтраль калибровки при обычном LOCK и
возврате трекинга. Проверка первой позы и явная перекалибровка остаются;
контроллеры не требуется возвращать к первоначальной позе после каждой
паузы. Фильтры и ограничитель скорости обеспечивают плавный возврат целей.

Если защита writer защёлкнула KILL, но control graph продолжает работать,
повторное нажатие **RUN** не перезапускает видео, VR bridge, DDS reader и
writer. Панель выполняет
`clear emergency → pause → calibrate → resume → fast prepare` через
`make exhibition-rearm`. Выполняет восстановление сам владелец сеанса со
своим первоначальным commissioning token. Восстановление после аварии может
занимать десятки секунд: оно включает повторную проверку и StandUp/Start.
Отсутствие свежего VR при обычном RUN не снимает KILL и не запускает эту
цепочку. Полный холодный запуск по-прежнему выполняет все проверки.

### Отклик выставочного профиля

Левый стик использует помощь прямому ходу: небольшая примесь второго
направления убирается до усиления и обрезания входа. Параметр bridge
`translation_axis_snap_ratio=0.60` сохраняет прямое направление примерно в
пределах 31° от каждой основной оси; дальше второе направление вводится
плавно, полная диагональ 45° сохраняется. Правый стик поворота не изменён,
скорости не повышены. Значение 0 возвращает прежнюю обработку. Проверка
нейтральных стиков при RUN/reconnect использует исходные оси и не обходится
этой помощью.

Для физического `wireless_controller` знаки бокового движения и поворота
преобразуются только в `r1_live_writer/src/transport.cpp`. На проверенном R1
положительный pilot LX двигает робота вправо, тогда как положительный ROS Y
означает движение влево; поэтому lateral инвертируется на границе транспорта.
Отрицательный ROS yaw (вправо) аналогично даёт положительный pilot RX. В Pico/ROS
bridge остаются стандартные ROS-знаки; режим LocoClient RPC и симуляция
не получают физическую инверсию Unitree. После изменения оператор физически
подтвердил правильное боковое движение влево и вправо; целевые C++ и
writer/bridge loopback-тесты также покрывают оба знака.

Панель задаёт `R1_RESPONSE_PROFILE=exhibition`; настройки ROS берутся из
`r1_teleoperation_app/config/response_exhibition.yaml`. Предыдущий отклик
доступен как `standard` в выпадающем списке настроек. Профиль применяется
при новом полном сеансе. Статические и отдельные commissioning-запуски
сохраняют стандартный профиль независимо от выбора панели.

Руки: лимит IK и writer 0.75 рад/с вместо 0.50. Голова: yaw/pitch
0.55/0.40 рад/с вместо 0.35/0.25. Входное сглаживание уменьшено согласованно
с writer. Это пределы команд, а не гарантия скорости физического сустава.
Угловые границы, PD gains, моторная диагностика, пределы ходьбы и B сохранены.
При официальном prepare временная поза головы не вызывает ложный отказ до
завершения StandUp; перед первой передачей ArmSdk абсолютная поза и её
стабильность по-прежнему проверяются.

Снимок исходников до изменения:
`backups/exhibition-working-20260925-045557/sources.tar.gz`.

Физический writer принимает только профиль `slow-safe`. Слово
`exhibition` здесь означает упрощённую оркестрацию и устойчивость к краткой
потере tracking, а не увеличение физических лимитов. Mapping остаётся
прежним: левый Y — вперёд/назад, левый X — вбок, правый X — поворот, правый Y
не используется.

Кнопки действий не пересекаются с осями стиков:

- `X` на левом контроллере возвращает обе руки в robot-neutral через штатное
  сглаживание и ограничение скорости. Пока X удерживается, neutral сохраняется;
  после отпускания руки автоматически возвращаются к VR-follow.
- `B` на правом контроллере немедленно обнуляет скорость, снимает session-arm
  и защёлкивает центральный KILL. Удержание B не повторяет запрос. Для
  продолжения B нужно отпустить и явно нажать RUN или «Снять аварийную
  остановку» в сервисном разделе.

До запуска control панель должна передать те же явные подтверждения, которые
требует live commissioning:

```dotenv
ROBOT_DRY_RUN=0
ROBOT_ENABLE_ACTUATION=1
ROBOT_CONFIRM_OFF_CHARGER=1
ROBOT_CONFIRM_CLEAR_AREA=1
ROBOT_CONFIRM_ESTOP_READY=1
ROBOT_CONFIRM_COMMISSIONING=1
ROBOT_COMMISSIONING_TOKEN=<одноразовый токен не короче 16 символов>
ROBOT_VR_SOURCE_IP=<фиксированный IP очков>
```

`make exhibition-control` явно выбирает `session_arm`; обычные `teleop-live` и
`r1-live-session` по умолчанию продолжают работать в режиме `deadman`. Для
настройки выставочной session-arm логики используются переменные:

```dotenv
R1_EXHIBITION_SESSION_MODE=session_arm
SAFETY_PROFILE=exhibition
R1_EXHIBITION_TRACKING_GRACE_SEC=2.0
R1_EXHIBITION_RECOVERY_BLEND_SEC=0.50
```

Допустимы только `deadman` и `session_arm`; grace period ограничен диапазоном
1–3 секунды. В `session_arm` bridge всё равно начинает разоружённым. Manager
запрашивает `/vr/teleop/arm_session` перед prepare вместо первого физического
Deadman press. Внутри writer `prepared_session()` выполняет обязательную
anti-stale re-arm последовательность и проверяет нейтральные стики. Manager не
отправляет внешний `disarm` после prepare: такое ребро означает реальный STOP
и защёлкивает KILL. STOP сначала вызывает `/vr/teleop/disarm_session`, а затем
независимый `robot-stop`. Выборочный reconnect не disarm'ит и не останавливает
исправный writer. Снятие KILL этими сервисами невозможно.

## Калибровка

1. Запустите control-сеанс и дождитесь стабильного tracking.
2. Manager переведёт session-arm в calibration pause: руки удерживаются,
   скорость ног становится нулевой, но writer latch не сбрасывается.
3. Смотрите прямо и держите обе руки неподвижно перед нижней частью груди.
4. После отдельного решения вернуть калибровку выполните
   `make exhibition-calibrate-arms`. Кнопки калибровки рук в панели сейчас
   намеренно отсутствуют, чтобы выставочный профиль нельзя было перезаписать
   случайно.

Последовательность всегда `pause_session → arms-calibrate → resume_session`.
`disarm_session` для калибровки не вызывается; resume принимается только при
свежем tracking и нейтральных стиках.

Профиль сохраняется в
`~/Unitree_Project/Configs/Calibration/r1_body_calibration.json` и загружается
следующим arm-сеансом. В файл входят независимые neutral offsets обеих рук;
workspace/joint limits остаются обязательными.

## Потеря связи и восстановление

- Падение POV не перезапускает robot writer. Video-only процесс
  перезапускается отдельно с backoff 0.5 → 1 → 2 → 4 → 8 секунд.
- Потеря tracking в `session_arm` не снимает session-arm защёлку: руки
  переходят в hold, а скорость ног становится нулевой. После возврата полного
  tracking руки автоматически и плавно возвращаются к новым позам. Ноги
  остаются на нулевой скорости до свежего пакета с нейтральными стиками, после
  чего управление восстанавливается автоматически, без повторного arm.
- Unity/Pico sender проверяет покомпонентные OpenXR-флаги `Position` и
  `Rotation`. Поэтому краткий сброс общего `isTracked` у контроллеров возле
  бёдер не считается потерей, пока runtime продолжает выдавать полноценную
  предсказанную позу, как в обычных VR-играх. Реальная потеря позиции или
  поворота всё равно включает описанный hold/zero режим.
- Ошибка SDK, motor feedback, связи с роботом или live writer остаётся
  критической: выставляется STOP/KILL, writer автоматически не
  перезапускается.
- При KILL от обратной связи повторно нажмите RUN. Если manager и control graph
  живы, панель использует быстрый `exhibition-rearm`; новый холодный graph не
  создаётся.
- `make exhibition-reconnect` — выборочное действие оператора. Исправные
  writer, VR/ROS graph и POV не перезапускаются. Завершившийся POV поднимается
  отдельно, не меняя режим робота. Исчезнувший writer считается safety fault:
  reconnect его не создаёт; после проверки условий требуется явный RUN.
- `make exhibition-stop` доступна независимо от состояния manager; она
  вызывает проверенный `robot-stop`, при отсутствии подтверждения —
  `robot-kill`, затем завершает все дочерние группы процессов.

Текущий статус:

```bash
make exhibition-status
tail -f logs/exhibition/control-*.log
```

## Проверка без робота

План можно посмотреть без запуска процессов:

```bash
R1_EXHIBITION_MOCK=1 ./scripts/r1-exhibition plan static
R1_EXHIBITION_MOCK=1 ./scripts/r1-exhibition plan control
```

Smoke/unit-тесты используют только подставные локальные процессы:

```bash
make exhibition-mock-smoke
```

Для ручного mock-сеанса, который не открывает Unitree transport:

```bash
R1_EXHIBITION_MOCK=1 make exhibition-static
# в другом терминале
R1_EXHIBITION_MOCK=1 make exhibition-stop
```

Mock viewer использует отдельный адрес `http://127.0.0.1:18080/`, а локальный
dry-run bridge — loopback UDP-порты `19090` (данные) и `19091` (discovery).
Поэтому проверка не останавливает постоянный video-only сервис и не конфликтует
с его обычными портами `8080`, `9090` и `9091`. Mock preflight проверяет только
локальные файлы, сборку и свободные альтернативные порты; Ethernet, камеры и
включённый робот ему не нужны.

## Офлайн-чек перед следующим включением

Пока робот выключен, этот порядок проверяет программные границы без физических
команд:

```bash
make head-dry-run
make arms-dry-run
make legs-dry-run
make teleop-dry-run-smoke
make head-live-dry-arm
make pov-preflight
make pov-demo
make operator-panel-smoke
```

Mock POV печатает URL с портом `18080`; stereo demo использует `18081`. Эти
порты не затрагивают постоянно работающий offline viewer на `8080`.
Head dry-run использует UDP `19130/19131`, а legs dry-run — `19132/19133`,
поэтому их можно запускать при активном offline bridge; при необходимости
порты меняются через `R1_DRY_RUN_UDP_PORT` и
`R1_DRY_RUN_DISCOVERY_PORT`.

`head-dry-run` и `head-live-dry-arm` публикуют только debug-траектории. Для
калибровки головы сначала должен работать один из этих графов, затем выполните
`make head-calibrate` и держите HMD неподвижно. После физического включения
следующий порядок на панели: **Проверить всё → Robot POV → Статичный режим →
Калибровать голову (смотреть прямо) → Режим управления**. Калибровка рук
вынесена в отдельный будущий commissioning и с выставочного экрана удалена.
Проверьте голову и руки по отдельности, затем стики/ноги и только после этого
полный arms+legs сеанс. На главном экране доступны подключение, LOCK, RUN,
СТОЙКА, Zero Torque, выборочное переподключение и Robot POV. Кнопок
калибровки рук там нет. STOP, KILL и снятие аварийной остановки находятся в
**Расширенные настройки → Аварийное**; Zero Torque также повторена там.
Явная аварийная кнопка во время VR-сеанса — `B` на правом контроллере.

Физический `make head-live` остаётся отдельной commissioning-командой, но
полный `exhibition-control` включает HMD→голова вместе с руками и ногами после
общих preflight, калибровки, session-arm и prepare. Первый тест после загрузки
всегда выполняется по осям: голова, руки, затем короткие импульсы стиков.
