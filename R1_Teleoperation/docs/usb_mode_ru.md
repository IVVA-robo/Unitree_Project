# Pico 4 Ultra по USB-C: автономная связь с ноутбуком

Цепочка: Pico (позы головы, контроллеров, кнопки) → USB-C/ADB → ноутбук
→ существующий ROS-контур → Ethernet → Unitree R1.
Видео камеры идёт в обратную сторону: R1 → Ethernet → ноутбук → USB → Pico.
Зеркало дисплея Pico выводится на ноутбуке отдельной программой scrcpy по USB.
Интернет и Wi-Fi для USB-режима не нужны. Установка инструментов и сборка
выполняются заранее; затем всё необходимое находится на ноутбуке.

## Что проверяется этим запуском

`scripts/r1-usb-session` — диагностический режим. Он передаёт реальные позы в
ROS-домен 91, в котором контроллеры работают в dry-run. Он **не включает
движение робота** и не меняет IP-фильтры физического управляющего контура.
Этот запуск подтверждает USB-транспорт. Для движения теперь есть отдельный
USB-режим штатной панели, описанный ниже. На момент этой исходной диагностики
физическое движение ещё не проверялось; поздние физические RUN/LOCK описаны
ниже. Физический обрыв кабеля при движении не объявляется проверенным.

## Управление движением без Wi-Fi

В настройках панели выбран **«USB-C — без Wi-Fi»**. Подключите Pico к ноутбуку
по USB-C, а ноутбук к R1 по Ethernet. Наденьте очки, включите контроллеры,
оставьте стики в нейтрали. Закройте отдельный диагностический USB-сеанс,
если он запущен: его туннели несовместимы с одновременным RUN.

Перед первым физическим запуском снимите робот с зарядки, освободите зону
движения, обеспечьте готовность аварийной остановки и отключите параллельное
управление с телефона. Затем используйте обычную кнопку **RUN** в панели.
Проверки Ethernet, SDK, готовности робота, калибровка и ограничения скорости
остаются штатными. Выбор USB сам по себе не запускает двигатели.

Фоновый `r1-connection-ensure` заранее поддерживает приложение Pico в
USB-режиме и отдельный read-only туннель `8080 → 8080`, в том числе до RUN и
во время СТОЙКИ. RUN запускает `usb_link.control` и добавляет только
эксклюзивный канал поз `19092 → 19092`; relay переводит их в локальный UDP
9090. При завершении RUN удаляется только `19092`, а приложение и `8080`
остаются для Robot POV. Фоновый helper использует тот же transport-lock и не
может вмешаться в активный control-сеанс; он не запускает ROS, writer или
команду роботу.

Wi-Fi очков во время RUN временно отключается и возвращается после штатного
STOP. Wi-Fi ноутбука не нужен, но автоматически не переключается. Интернет во
время работы не требуется. Зеркало экрана можно открыть командой
`./scripts/r1-usb-mirror`.

При отсутствии пакетов более 250 мс мост обнуляет ходьбу, удерживает
последние позы и фиксирует паузу сеанса. Восстановление потока не снимает
паузу: отпустите стики и нажмите RUN. При потере самого моста/писателя
действуют существующие независимые watchdog и STOP/KILL. Это программные
защитные реакции; фактическую остановку и баланс робота ещё нужно проверить
в контролируемом физическом испытании. Кабель не заменяет аварийную кнопку.

USB принимает только источник `127.0.0.1`; режим должен явно совпадать
в параметрах и окружении физического писателя. Обычный LAN-режим по-прежнему
не принимает loopback. Автоматического перехода на Wi-Fi нет. Расширенные
поэтапные тесты через `r1-live-auto-run` остаются LAN-инструментами;
USB-управление запускайте через основной RUN.
Менять USB/LAN в настройках нужно только после завершения текущего сеанса
через STOP: уже запущенный управляющий процесс сохраняет выбранный транспорт.

Проверка интеграции без робота: реальный TCP-ретранслятор → UDP-мост → ROS
в отдельном домене 92. Разрыв TCP обнулил команду скорости, повторное
подключение оставило паузу, удерживаемый стик заблокировал возобновление,
явный запрос с нейтральными стиками восстановил активность. Физический
писатель в этой проверке не запускался.

Дополнительно прошли 282 функциональных Python-проверки (без общих lint-тестов)
и все 8 наборов CTest модуля `r1_live_writer`. Общие lint-тесты, запущенные из
корня, обнаружили замечания стиля по всему репозиторию; это не чистый lint-run.
Новые файлы USB-интеграции проверены отдельно. В mock-smoke исправлен парсер,
который ошибочно считал числа из предупреждения ROS о потере сообщения
позициями суставов; добавлены две регрессионные проверки этого случая.
Повторный полный `r1-live-writer-mock-smoke` прошёл: блокировка без разрешения,
prepare/rearm, KILL, отпускание deadman, watchdog головы и скорости. Он работал
в отдельном сетевом пространстве только с loopback и `MockTransport`;
физический SDK-транспорт не запускался.

Стандартный Wi-Fi-запуск APK сохранён. USB выбирается параметром Android
`--ez r1_usb true` при запуске приложения. В USB-режиме автоматического
перехода на Wi-Fi нет. Для смены режима приложение нужно полностью закрыть.

## Запуск

Подключите Pico к ноутбуку кабелем USB-C ↔ USB-C с передачей данных.
Наденьте очки и включите оба контроллера. Снятый с головы Pico может заснуть:
тогда остановятся и трекинг, и изображение, даже при исправном кабеле.
USB debugging уже разрешён на проверенном Pico. После сброса настроек
может потребоваться снова подтвердить доверие этому ноутбуку в очках.

Из `/home/unitree/Unitree_Project/R1_Teleoperation`:

```bash
./scripts/r1-usb-session --wifi-off
```

Появится тестовое видео, а трекинг поступает с настоящих очков и контроллеров.
`--wifi-off` временно отключает Wi-Fi **очков** и возвращает его при штатном
завершении. Wi-Fi ноутбука эта команда не переключает. Чтобы остановить,
нажмите Ctrl-C в этом терминале.

Для изображения камеры физического робота вместо тестового:

```bash
./scripts/r1-usb-session --wifi-off --video-source unitree
```

Этот вариант использует существующий источник камеры по Ethernet, но всё
ещё оставляет управление движением в dry-run. Если камера робота недоступна,
наличие USB-связи само по себе не восстановит видеосервис на роботе.

Второй терминал для зеркала экрана:

```bash
./scripts/r1-usb-mirror
```

Сервер видео для ноутбука: <http://127.0.0.1:18080/>.
Текущее состояние трекинга:

```bash
source /opt/ros/humble/setup.bash
ROS_DOMAIN_ID=91 ROS_LOCALHOST_ONLY=1 RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
  ros2 topic echo --once --full-length /vr/teleop/status std_msgs/msg/String --no-daemon
```

При обрыве кабеля поток прекращается, а watchdog диагностического моста
помечает его устаревшим. При завершении с отключённым кабелем вернуть Wi-Fi
очков можно в меню Pico либо после подключения командой:

```bash
adb shell svc wifi enable
```

Чтобы вернуться к Wi-Fi-приложению после завершения USB-сеанса:

```bash
adb shell am force-stop com.ionosrobots.unitree.telepresencedemo
adb shell am start -n com.ionosrobots.unitree.telepresencedemo/com.unity3d.player.UnityPlayerActivity
```

## Почему ADB

На проверенной прошивке команда включения RNDIS вернула Pico к
`mtp,accessory,adb`; USB-сетевой интерфейс не появился. Поэтому используется
работающий ADB-транспорт. `adb reverse` переносит TCP, но не UDP: для поз
добавлен запрос–ответ с уникальным токеном. Ответ старше 200 мс, неверный
токен или некорректный пакет закрывают соединение и не попадают в ROS.
После переподключения требуется заново отпустить grip перед его активацией.

Диагностические порты: Pico TCP 19092 → ноутбук TCP 19092 (позы), Pico TCP 8080 → ноутбук
TCP 18080 (HTTP/MJPEG видео). Ретранслятор отправляет только на локальный
UDP 19090, диагностический discovery — 19091. Приёмники привязаны к
127.0.0.1. Ввод из сети Wi-Fi к этим портам не нужен.

## Покупки

- Для первого запуска ничего покупать не требуется: существующий кабель
  уже обеспечивает ADB со скоростью USB 2.0 (480 Мбит/с).
- Для рабочего комплекта: гибкий кабель USB-C ↔ USB-C с явным указанием
  передачи данных USB 3.x, 5 Гбит/с или выше. Надпись «100 Вт»/«240 Вт»
  описывает питание и не гарантирует высокую скорость данных. На 3–5 м
  предпочтителен качественный активный VR-кабель с проверенной совместимостью.
- Для длительных сеансов: при необходимости кабель/инжектор питания,
  специально поддерживающий одновременно USB-данные и питание Pico.
  Обычный Y-разветвитель USB-C для этого не подходит. Даже подключённые
  по USB очки могут разряжаться, если порт ноутбука отдаёт мало мощности.
- Ethernet уже подключён через TP-Link; его достаточно для проверки.
  Если потребуется замена, выбрать USB 3.x Gigabit Ethernet с поддержкой
  штатным драйвером Linux. Это отдельный канал ноутбук → робот.
- Нужна разгрузка кабеля на оголовье, чтобы натяжение не приходилось на
  разъём Pico. Для USB-режима роутер, интернет и карта видеозахвата не нужны.

Картинка scrcpy — зеркало дисплея, доступного Android. Она может отличаться
от полного стереоскопического поля зрения и системных защищённых слоёв Pico.
Для управления используются численные позы и кнопки, а не анализ картинки.

## Бэкап и восстановление

### Переключение RUN → СТОЙКА → RUN

Доработки надёжности 29.09:

- STOP прерывает длительные подготовительные проверки; их дочерние процессы
  завершаются своей группой. Затем остаётся обязательный STOP/KILL менеджера.
- При смене режима можно выбрать другое назначение перехода. Явный STOP
  отменяет отложенный запуск; нажатие во время STOP/Zero Torque не ставит
  движение в очередь на последующее автоматическое включение.
- Ошибка запуска процесса завершает действие с ошибкой, освобождая кнопку
  для повторной попытки. Старт программы не означает подтверждённую стойку.
- Сбой USB relay: до трёх попыток восстановления за минуту, только после
  подтверждённого LOCK текущего владельца. Движение возобновляется явным RUN.
  При невозможности LOCK или повторяющихся сбоях выполняется штатный STOP.
- Перезапуск видео не снимает degraded/blocked/LOCK. Он не доказывает, что
  физический управляющий процесс готов.
- Для «Стойки» используется тот же сокращённый путь подготовки, что для RUN:
  после завершённой SDK-проверки и готовности нового графа её не повторяют.
  Совпадение commissioning token, featureless static-параметры, свежая
  обратная связь, отсутствие активного ArmSdk и подтверждение FSM 4 обязательны.
- Проверка ROS-графа и поиск read-only SDK reader используют по одному
  участнику discovery вместо нескольких запусков ROS CLI. Проверки типов,
  разрешений и свежих 26 конечных значений суставов сохранены. При неизвестном
  или уже существующем, но недоступном reader второй не запускается.
- Панель не ждёт ADB в UI-потоке: USB проверяет владелец транспорта до запуска
  менеджера. Фоновая SDK-проверка завершается асинхронно с очисткой своего
  reader; до её подтверждённого завершения режим не запускается. STOP и
  Zero Torque отменяют отложенный RUN; строка READY сама его не разрешает.
  Панель отслеживает непосредственно SDK worker, без make-обёртки, которая
  могла завершаться раньше его очистки. Повторный STOP не обрывает очистку;
  закрытие окна отменяет отложенный режим и ждёт завершения worker.

RUN ↔ LOCK сохраняет запущенный граф. «Стойка» — настоящий отдельный режим
FSM 4, не переименованный LOCK. Холодный запуск и восстановление после KILL
могут занимать больше времени; таймеры безопасности не сокращаются ради UI.
Нельзя обещать отсутствие любых аппаратных/сетевых ошибок. Восстанавливаются
только проверяемые сбои транспорта; неподтверждённые физические состояния
остаются блокировкой, а не поводом автоматически снимать KILL.

После защёлкнутого KILL явный RUN завершает старый управляющий граф через
проверенный STOP/KILL и запускает новый с preflight, калибровкой и prepare.
USB-владелец, relay и видео сохраняются. Это отдельный, более медленный путь,
чем обычный RUN ↔ LOCK: старый инициализированный SDK-процесс иначе оставляет
DDS publisher и блокирует проверку одного источника команд рук. Проверку
`expected-writers=1` не ослабляют; после неудачной попытки новый RUN не пытается
поставить уже disarmed VR-сеанс на паузу. После контакта с препятствием нужно
сначала устранить контакт и проверить робота; автоматического возобновления нет.

Проверено на физическом роботе 29.09: RUN ↔ LOCK при выключенных Wi-Fi
ноутбука и Pico, без default route — 2.32 s для возобновления и 3.59 s для LOCK.
При искусственном сбое relay восстановился за 0.76 s, сохранив LOCK и того же
менеджера. Обратная настоящая «Стойка» подтверждена FSM 4, но весь переход
занял около 49 s. Последующее сокращение discovery и асинхронная работа панели
проверены программно и по read-only телеметрии. После исправления make-handoff
повторная физическая «Стойка» из остановленного сеанса заняла около 25 s
(16:27:46–16:28:11): ready_static 5.780 s, prepare 16.508 s, стабильный FSM 4.
SDK preflight был в текущем кэше, Wi-Fi в этом замере не отключался.
Полный обратный переход из USB/RUN на новой версии ещё требует повторного
замера. Нельзя считать время одного probe (около 3 s вместо 10.3 s)
временем полного переключения режима.

Протокол и журналы: `logs/offline-reliability-20260929/RESULT.md`.

### Программная проверка без робота на время зарядки батареи

29.09 дополнительно исправлены обработка статусов и подтверждения кнопок:

- Текстовый тест отличает полный статус writer от служебного события
  «связь восстановлена». Событие не подменяет статус и не продлевает его
  свежесть. KILL, неполные или устаревшие данные по-прежнему прерывают тест.
- LOCK при пропавшем ответе повторяет только запрос паузы, один раз,
  в пределах прежнего общего таймаута. Успех требует ответа сервиса и новых
  подтверждений состояния. RUN, arm и снятие аварийной блокировки не повторяются.
- Повторный LOCK после ошибки ждёт результат нового нажатия, а не возвращает
  прошлую ошибку. Журнал helper сохраняет этап ожидания и последние признаки
  состояния даже при завершении по внешнему таймауту.
- Повторный STOP после подтверждённой очистки не обращается к уже закрытым
  ROS-сервисам, только если под блокировкой сеанса повторно проверены запись
  состояния и отсутствие USB-владельца/локальных управляющих процессов.
  Старого state-файла или исчезновения PID недостаточно; при неопределённости
  остаётся прежний STOP/KILL-путь.

Проверка без робота: **461 passed in 46.84s**. Весь прогон выполнялся в отдельном
сетевом пространстве с одним loopback. ROS-имитатор в домене 231 подтвердил
пять циклов RUN→LOCK, задержку ответа LOCK, запрет RUN при KILL и отказ при
отсутствии свежего подтверждения. Робот, Pico и Wi-Fi в этом прогоне не
переключались. Это программные проверки, не доказательство физических
скоростей/баланса. Причина аппаратного таймаута LOCK в 17:10 точно не
установлена; добавлены диагностика и безопасная обработка потерянного ответа.

Нужна повторная физическая приёмка RUN→LOCK при обоих Wi-Fi off и отдельная
проверка явного RUN после KILL. Текстовые подсказки нового теста — в отдельном
окне ноутбука, без озвучивания. Периодические ошибки JPEG камеры также не
объявляются устранёнными этими изменениями.

Обычный способ — кнопки панели. При смене режима сначала выполняется
проверенная остановка робота, затем завершаются pose relay и эксклюзивный
туннель `19092`, и только после этого запускается новый режим. Приложение Pico
и read-only туннель `8080` сохраняются; видеосервер нового режима продолжает
работать на том же локальном порту. При незавершённой очистке новый запуск
блокируется; можно повторить после её завершения. Обрыв связи и KILL не дают
разрешения автоматически двигаться.

Контрольный тест старой загруженной версии 02.10 показал дефект этого handoff:
RUN → СТОЙКА занял `20,20 s`, приложение на Pico закрылось, а после ручного
открытия видео без Wi-Fi не было. Ноутбук при этом имел исправный локальный POV,
а `adb reverse --list` был пуст. Исправление выше прошло `45` изолированных
USB/video mock-тестов. После штатного STOP и выключения робота панель была
перезапущена с исправлением 02.10 в 11:13:12. Автозапуск создал ровно один
offline POV и только `tcp:8080 → tcp:8080`; manager, writer и `19092`
отсутствовали. Контрольное удаление mapping восстановилось watchdog за
`4,258 s`, PID приложения Pico `10049` не изменился. Физический тест полного
перехода с новой панелью выполнен: после СТОЙКА → RUN → LOCK оператор
подтвердил сохранение видео.

Финальный повтор 02.10 проведён при выключенном Wi-Fi. Оператор несколько раз
выполнил СТОЙКА → RUN → LOCK; видео в очках сохранялось, ошибок панели не было.
Перед этим повтором исправлена гонка handoff: предыдущий static writer уже
завершался, но кратко оставался видимым в `/proc`, из-за чего USB RUN ошибочно
сообщал `Stop the active robot control session before USB diagnostics`.
Wrapper теперь ограниченно ждёт завершения очистки до 12 секунд, проверяя её
каждые 50 мс. До исчезновения writer новый manager не запускается. Если writer
действительно активен или завис, запуск завершается блокировкой; тайм-аут можно
настроить `R1_USB_LIVE_CLEANUP_WAIT_SEC` только в диапазоне `0…30` секунд.
KILL, deadman, watchdog и writer-count gate не изменялись.

USB/handoff тесты после исправления: `50 passed`. Отдельный реальный `/proc`
тест дождался искусственно завершающегося writer за `394 ms`. В пяти журналах
физических повторов нет `[BLOCKED]`/`[FAIL]`; FSM 4/811 подтверждены,
дубликатов manager, writer, VR bridge и POV не найдено.

Для запуска из терминала с уже полученными актуальными подтверждениями
безопасности предусмотрен `scripts/r1-usb-run-service`. Он сохраняет
переданные настройки и не создаёт подтверждения за оператора. Сервис не
перезапускается автоматически; SIGTERM передаётся только своему менеджеру,
который выполняет штатный STOP/KILL. У сервиса намеренно **нет ExecStop**.
Нельзя добавлять `ExecStop=.../r1-exhibition stop`: после естественного
завершения старого RUN такая команда может остановить уже новую «Стойку».
