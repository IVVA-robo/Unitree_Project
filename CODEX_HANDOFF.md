# Передача проекта новому чату Codex

Актуальность: 01.10.2026. Это сводка рабочего контекста по коду, журналам и
сообщениям оператора; **не дословная выгрузка всей переписки** и не показания
робота в реальном времени. История Git, прежние README и отчёты сохранены отдельно.

## Сообщение, которое можно отправить новому чату

> Работаем с Unitree R1 и Pico 4 Ultra. Репозиторий:
> https://github.com/IVVA-robo/Unitree_Project .
> Прочитай AGENTS.md, CODEX_HANDOFF.md, README.md, TRANSFER_STATUS.md.
> Сначала сообщи, что уже реализовано, что осталось и что доступно сейчас.
> Не запускай движение, Zero Torque, физические тесты и перезапуски служб без
> моего отдельного подтверждения. Не убирай защиты. Говори по-русски текстом.
> Материалы ноутбука уже опубликованы. PC2 не удаётся включить, прежняя проблема
> сохраняется; его файлы ещё не получены. Не рассчитывай на обычное включение.
> Дальнейшую задачу согласуем: диагностика PC2 либо продолжение работы с
> доступным софтом и надёжностью проводного режима.

Новый чат должен иметь доступ к репозиторию/клону. Одна ссылка сама по себе
не передаёт SSH-доступ, секреты, подключённое оборудование и гигабайты LFS.

## Цель пользователя

Полностью автономное управление без Wi-Fi и интернета:
Pico USB-C ↔ ноутбук Ethernet ↔ R1. Сохранить нынешнюю рабочую версию,
максимально надёжные кнопки и быстрое переключение режимов, понятные подсказки
перед любым действием оператора. Последняя задача — перенести все относящиеся
к роботу материалы в GitHub и сохранить контекст для продолжения в новом чате.

Пользователь плохо понимает озвучку: **только письменные инструкции**.
Он сам умеет нажимать RUN/LOCK/СТОЙКА; предупреждать заранее.
Фраза «продолжай без робота» разрешает программную работу, не физические команды.

## Что реально собрано

- Ноутбук: Ubuntu 22.04, ROS 2 Humble, активный проект
  /home/unitree/Unitree_Project/R1_Teleoperation.
- Pico 4 Ultra / Android 14, два контроллера; APK с R1UsbPoseTransport.
- USB-владелец и локальный relay получают позы/кнопки; ROS использует их для
  IK, головы/рук и ходьбы. Для ходьбы нужен корректный grip, не только стик.
- Ethernet SDK/DDS связывает ноутбук с контроллером .161.
- Реальная камера → video hub → MJPEG/HTTP → USB reverse → Pico.
  scrcpy отдельно зеркалит доступный Android-дисплей.
- PC2 .164 использовался для дополнительных сервисов, в том числе voice;
  его текущие исходники нужно прочитать на самом PC2, не угадывать по ноутбуку.

Подробные адреса, зависимости и режимы — в README. Системные ярлыки и unit-файлы
скопированы в Deployment/Laptop как данные; не устанавливать их автоматически.

## История основных этапов

1. Ранее существовали симуляция, UDP/Wi-Fi teleop и Robot POV.
   Исходные версии сохранены в Git, Legacy_Robotics и Backups.
2. 29.09 добавлены USB-позы и обратный видеотуннель; созданы снимки до USB и
   до физического live-режима. Проверены поток около 45 Hz и видео около 15 FPS.
3. В диагностическом графе отдельно проверены Wi-Fi off, отсутствие default route,
   кнопки/sticks и deadman. Диагностика не является физической приёмкой.
4. Оператор подтвердил успешные стойку, RUN, LOCK, управление руками и ходьбу.
   Сначала наблюдалось «только торс, не ходит»; текущие выставочные настройки
   используют slow-safe 0,20/0,12 м/с и 0,35 рад/с, leg_speed_scale=1,0.
5. Проводились физические RUN ↔ LOCK при обоих Wi-Fi off:
   примерно 2,32/3,59 с. Восстановление relay в LOCK — около 0,76 с, без auto-RUN.
6. Исправлены передача владения при смене режима, асинхронный SDK worker,
   отмена pending RUN после STOP, обработка повторного STOP/LOCK и статусы.
   Реальная ошибка make-handoff воспроизведена: make завершался раньше cleanup
   worker. Панель теперь запускает worker напрямую.
7. При контакте со столом, а позднее при раскачивании человеком робот
   останавливался. Оператор сообщал об устранении контакта и отсутствии
   видимых повреждений. Это не обоснование отключать защиту или специально
   повторять столкновения.
8. 30.09 добавлен автоматический сброс SDK-attestation при запуске warmup,
   потере линка и периодическом обновлении. Полная приёмка этого пути после
   перезапуска робота ещё не завершена: ручная SDK-проверка работала, фоновое
   получение attestation через панель в последней сессии оставалось проблемой.
9. Материалы ноутбука опубликованы на GitHub, наличие LFS-объектов проверено.
   Пользователь уточнил: **PC2 не удаётся включить, прежняя проблема сохраняется**.
   Его файловая система не собрана. Причина отказа не установлена; диагностика
   или ремонт не выполнялись в рамках публикации.
10. 01.10 главный выставочный экран и обработчики оптимизированы без изменения
    IP, портов, Ethernet/USB-схемы и `ROS_DOMAIN_ID=88`. Кнопки калибровки рук
    удалены по решению оператора. Static readiness передаётся prepare через
    одноразовую HMAC-аттестацию, а финальные safety service call выполняет один
    bounded ROS-клиент. Исправный `r1-offline-session.service` и его Robot POV
    теперь переиспользуются в СТОЙКЕ; RUN сохраняет полный port handoff.
    Сопоставимый физический переход СТОЙКИ ускорен примерно
    `21 → 17 → 14 → 10,460 s`. Последний сеанс подтвердил стабильный FSM 4,
    один manager/writer/POV/bridge и healthy reconnect за `0,305 s` без смены
    PID. POV теперь перезапускается отдельно самим ROS launch; живой crash-test
    восстановил поток за `5,716 s`, сохранив VR bridge, manager и writer.
    Полный loopback-only прогон: `375 passed in 52.17s`.

Не считать эту хронологию стенограммой или независимым аудитом каждого события.
Для чисел и программных изменений сверять отчёты и код.

## Что проверено, а что нельзя обещать

- Зафиксированы полноценные физические RUN/LOCK без Wi-Fi.
- Полные переходы RUN → СТОЙКА и холодный запуск не стали «за секунду».
  Последний сопоставимый static start занимает `10,460 s`; старые замеры
  около 25–79 с относятся к прежним версиям и другим условиям. Отдельный
  холодный RUN после оптимизации проверялся примерно за `39,27 s`.
- По отчётам были прогоны 380, 382 и 461 программных тестов.
  Это исторические результаты соответствующих версий, не новый прогон
  всего текущего дерева во время публикации.
- Потеря приложения/сон очков проверялись; физическое выдёргивание кабеля
  во время движения не объявлять успешно пройденным.
- Периодические JPEG-ошибки не доказаны полностью устранёнными.
- Автокэш, static HMAC-readiness и единый prepare-клиент программно и
  поэтапно физически проверены. Не сокращать обязательный 2,25-секундный
  ArmSdk traffic gate и reader/writer проверки ради дальнейшего ускорения.
- Логи, PID, last-ready и state.json устаревают. На момент передачи оператор
  сообщил, что PC2 не удаётся включить. Это не доказывает отключение управляющего
  компьютера .161 или моторов; на ноутбуке могли оставаться живые процессы.
  Никакой старый LOCK/ready не является доказательством текущего физического
  состояния. Перенос файлов не выключал робота и не останавливал службы.

## Рекомендуемый следующий порядок

1. Читать TRANSFER_STATUS; проверить Git/LFS и отсутствие незавершённой загрузки.
2. Копирование PC2 заблокировано невозможностью включения. Диагностику/ремонт
   согласовать отдельно, не выполнять автоматически разборку, сброс или
   переустановку. После восстановления доступности подтвердить Ethernet/SSH .164, снять read-only
   архив Tools/GitHub/collect_robot.py в новый частный локальный каталог.
   Сначала изучить список каталогов: defaults — отправная точка, не обещание
   охвата всего диска. Добавить фактически найденные robot-related проекты.
3. Проверить архивы на секреты, сохранить права/структуру и добавить в GitHub
   фактические PC2-конфиги/исходники с отдельным README.
4. Для warmup сначала собрать текущие журналы и окружение панели/worker;
   воспроизвести отличие ручного preflight и фонового. Не выдавать гипотезу
   о cold boot/таймауте за доказанную причину.
5. Выполнить программную регрессию в изоляции. Физические проверки — только
   после нового подтверждения оператора, по одному переходу, с замером этапов.
6. Обновить этот файл и отчёт фактами, отличая software-only от hardware тестов.

Текущий подробный отчёт по кнопкам и замерам:
`R1_Teleoperation/docs/exhibition_panel_optimization_20261001.md`.
Остаются отдельные физические проверки Zero Torque на надёжной опоре,
и полного cold-start после перезагрузки ноутбука. Принудительный отказ только
POV уже проверен. Ни одна оставшаяся проверка не требуется для уже
подтверждённой СТОЙКИ.

## Защиты и прошлые ошибки, которые нельзя вернуть

- Не должно быть двух независимых writers/владельцев USB; writer-count=1
  остаётся обязательной проверкой.
- Нельзя запускать RUN по одной строке READY, пока worker не закончил cleanup.
- STOP/Zero Torque отменяют очередь нового движения.
- Не добавлять ExecStop=r1-exhibition stop старому USB RUN unit:
  поздний cleanup прежнего владельца может остановить новую стойку.
- Восстановление камеры не снимает LOCK/KILL/degraded.
- Нельзя автоматически продолжать ходьбу после USB-gap/потери tracking.
- Запрещён старый физический head-recenter. Не путать его с проверенной
  seed/feedback-подготовкой нового пути.
- При USB >250 мс без пакетов ходьба обнуляется, сеанс требует явного
  возобновления по штатному протоколу.
- Нельзя запускать стендовые commissioning/probe команды поверх живого RUN.

## Что намеренно не передано в публичный репозиторий

SSH private keys, GitHub auth, пароли, частные профили NoMachine, файлы .env,
полная приватная история приложения Codex, ОС и пересоздаваемые build-кэши.
Это не препятствует чтению проекта новым чатом, но полный доступ к оборудованию
и восстановление окружения требуют отдельной настройки.
