## Повторная приёмка после возвращения оператора

Оператор заново подтвердил условия безопасности и сообщил, что робот стоит.
В 16:21 read-only API 7001 подтвердил FSM 4; менеджер оставался остановлен.
После первого нажатия «СТОЙКА» новый управляющий процесс не появился.

Причина воспроизведена отдельным интеграционным тестом реального QProcess:
панель запускала worker через make; при SIGTERM make выдавал finished(code=15)
до завершения cleanup worker. Добавленная проверка кода завершения правильно
отменила отложенную активацию, но сам путь передачи управления был неверным.
Прежний тест проверял прямой запуск скрипта и не охватывал make-обёртку.

Исправлено: панель напрямую запускает scripts/r1-sdk-warmup в отдельной группе;
finished теперь относится к самому владельцу cleanup. Повторные сигналы
во время его cleanup игнорируются до завершения собственного preflight.
Закрытие окна отменяет pending_warmup и асинхронно дожидается очистки.
Интеграционный тест проверяет реальный QProcess, повторный STOP и то, что
маркер очистки существует уже в обработчике finished с кодом 0.

Общий прогон один раз обнаружил нестабильное сравнение времени запуска
дочернего Python в test_loco_state_watch: само создание subprocess зависело
от нагрузки. Проверка перенесена на записанные начала запросов capture,
то есть на фактическое ограничение частоты. Код read-only watcher не изменён.

Итог после исправления make-handoff: **382 passed in 42.92s**,
git diff --check, bash -n, compileall — без ошибок. Панель перезапущена
в 16:26:39, без активного менеджера; автоматического физического запуска нет.
